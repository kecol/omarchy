# Guard direct host agent commands

**These guards prevent mistakes; they are not a sandbox or a security boundary.** Absolute executable paths, shell aliases/functions, IDE extensions, other PATH settings, and other shell integrations can bypass them. Container mode alone does not restrict a host process's permissions.

The guards are optional. They do not replace installed binaries, mise shims, account wrappers, or user scripts. They create separate scripts earlier in PATH for discovered agent commands that are currently available.

## Enable and inspect

```bash
omarchy agent guards enable
omarchy agent guards status
```

Use a new Omarchy Bash terminal after enabling. To apply the PATH integration to an existing Bash terminal:

```bash
source "$OMARCHY_PATH/default/agents/guard-path.sh"
omarchy_agent_guard_init
hash -r
```

Status lists the managed command names and whether each guard currently comes first on PATH. A false `first_on_path` value means that the current environment can bypass that guard. Aliases and shell functions are not included in this test. Bash restores guard precedence after mise's prompt hook. Other shells must arrange their PATH explicitly; no universal shell coverage is claimed. SSH commands or scripts that do not load Omarchy's environment setup can also bypass this integration.

In Host mode, a guarded command delegates to the underlying executable. In Container mode, it prints an agent-specific explanation and exits with status 126 without starting that host agent. An unreadable or invalid mode blocks the direct launch rather than assuming Host. An absent mode retains Omarchy's existing Host default.

A Pi launch instruction can look like this:

```bash
omarchy agent --inline --container --agent pi
```

**The direct container CLI mounts the selected project read-write.** It does not create an isolated clone. A definition check does not prove that an image exists, the engine works, or authentication is available. When no supported container launch is configured, the guard reports that instead of giving a command that this Omarchy version cannot support.

## Future agents and aliases

Discovery uses the existing default-agent menu catalog, built-in container definitions, user container definitions, and explicit registrations. It does not run an agent, install a tool, or search provider credentials to discover names.

After installing a new tool, adding a definition, or updating the catalog, refresh the generated guards:

```bash
omarchy agent guards sync
```

There is no background watcher. New catalog entries and future harness definitions do not require changes to a fixed list of agent products, but their guard scripts must be generated by enable or sync. Merely running sync does not enable a disabled guard system.

A container definition may declare optional `guardCommands` for additional direct executable names:

```json
{
  "name": "future-agent",
  "harness": "future-harness",
  "runtime": "podman",
  "command": ["future-cli"],
  "guardCommands": ["future-agent", "future-cli"]
}
```

Without that field, discovery considers the definition's agent name and first command token. Known general-purpose runners and system commands are excluded: a definition that uses Python must not replace Python with an agent guard. Explicit generic aliases are rejected. Conflicting automatic command mappings also fail rather than selecting an arbitrary agent.

To register a separate command name without changing a container definition:

```bash
omarchy agent guards register future-cli future-agent
omarchy agent guards sync
```

This only registers a guard mapping. It does not implement a new launcher or provide a container image. Remove a manual registration with `omarchy agent guards unregister future-cli`, then sync. Catalog and definition entries remain authoritative; unregister is not a general exclusion list.

## Deliberate Host and maintenance operations

Per-launch overrides remain available:

```bash
omarchy agent --inline --host --agent pi
```

For a deliberate direct Host command, including version checks, login, or updates:

```bash
omarchy agent guards host -- pi --version
```

The Host escape removes the guard directory from that child process's PATH. It does not change the saved mode. This is an explicit bypass, not a confinement mechanism; a new shell can load its own PATH integration again.

Omarchy's explicit agent Host launch paths and account-add/sign-in flow bypass the command guards for their existing host work. Sign-in does not become a container operation. Other scripts that call guarded names directly can still be blocked, including version probes and installers. Use an explicit Host maintenance command when intended. Existing agents are never stopped or moved by enabling guards or changing mode.

## Disable or remove

```bash
omarchy agent guards disable
omarchy agent guards uninstall
```

Disable immediately makes existing generated scripts delegate, even in terminals that still have the guard directory on PATH. It does not require a valid mode value. Uninstall removes only unchanged managed guard scripts and their empty bin directory. Manual registrations are retained for a later enable. Neither command changes installed tools or the launch default.

If a managed guard was edited or foreign files appear in its directory, sync/uninstall refuse to overwrite or delete them. Disable remains available for recovery when metadata is valid. Do not use this private guard directory for unrelated executables.
